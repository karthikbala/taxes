## What the owner must arrange

1. Invite the colleague's actual GitHub username as a collaborator on the private karthikbala/taxes repository. No collaborator was guessed or invited during export.
2. Grant them editor access to this existing Site through the owning Sites/Work workspace or Site sharing settings. GitHub access alone does not grant hosting/deployment access. The colleague must use their own authorized account.
3. Share the hosted POC access key through a password manager if they need to call the deployed API. The original local file is .poc-access-key.txt in the prior app checkout; that file is intentionally absent from this repository. 4. Production secrets stay in the Site runtime. Grant appropriate administration access; never copy secret values into repository files. Direct Cloudflare administration/DNS changes require the appropriate Cloudflare account permissions, but these are unnecessary for a normal local clone.
5. Assign one maintainer to integrate shared adapter changes and publish releases.

## Publishing through the existing Sites workflow

For a maintainer with authorized Sites tools:

1. Read .openai/hosting.json and call get_site for that exact project; retain audience. Verify current saved source/deployment and check paid reservations/running jobs before source runtime changes.
2. Use the existing Sites source-opening helper with a short-lived source repository credential held only in memory/stdin. This syncs the managed cloud source. Never paste its token into shell arguments, files or logs.
3. Transfer the reviewed GitHub changes into that source checkout. Record both the GitHub commit and resulting Sites source commit. Resolve differences; never overwrite concurrent cloud source or claim the two repositories automatically synchronize.
4. Run the narrow offline checks and build. Push the exact managed source state, package the corresponding build, save a version, and deploy that saved version. Preserve the current public audience and custom domain.
5. Verify final deployment status, capabilities, authentication, UI and relevant source-to-JSON acceptance. Use bounded approved live tests only when changed behavior needs them. Preserve earlier working source until the replacement is accepted.

The Sites helper scripts are part of the installed Sites plugin; they are not required for local npm setup. See the current installed Sites skill for its publishing commands and API schemas. If the colleague does not have that tooling/account access, do not claim npm run build or a GitHub push deployed production. Hand a reviewed commit to the authorized Site maintainer instead.

## Direct Wrangler / another hosting account

wrangler.local.jsonc is **local-only** with a placeholder database ID; never use it to deploy production. The generated build is a Cloudflare Worker, but directly deploying to another Cloudflare account requires deliberate configuration of a real Worker, D1 database, secrets, domain/routes and migration of the existing reservation/spending state. This repository does not provision or authorize that migration. It was not performed during handoff.

## Deleting the original Mac checkout

The cloud application and cloud D1 data continue running after local deletion. Remove local files only after a clean GitHub clone works, the hosted access key is backed up, and teammate repository/hosting access is arranged. Local .wrangler/state and .dev.vars are disposable development state, never production backups. Dated reports and the source-derived fixtures required for continuation are included under docs/evidence and tests/fixtures.
